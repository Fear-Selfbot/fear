# Ревью Fear

Состояние проверено по исходникам репозитория. Компиляция Python-файлов прошла; `uv lock --check` прошёл. Автоматических тестов, линтера и CI в репозитории не обнаружено. Сетевые сценарии с Telegram не запускались.

## Подтверждённые замечания

### High — повторный запуск BotFather-сценария не ограничен

**Файл:** `src/core/mixins/user.py:86-115`, вызывается из `src/core/client.py:98-105`.

Если BotFather не отвечает в заданные `send_message_wait` 30 секунд, метод возвращает `None`. `__get_token()` трактует отсутствие ответа `/token` как отсутствие бота, вызывает создание бота и рекурсивно повторяет получение токена без лимита попыток. При проблеме сети, лимите Telegram или несовпадении ответа процесс может бесконечно задерживать запуск и создавать повторные боты.

**Исправление:** ограничить попытки и общее время, проверять каждое ожидаемое сообщение до следующего шага, распознавать известные ответы BotFather и завершать запуск понятной ошибкой. Не создавать бота только на основании таймаута. **Проверка:** мокнуть последовательности таймаута и ошибок BotFather; убедиться, что число вызовов ограничено и создание бота не вызывается при отсутствии ответа.

### Medium — ошибка отправки может быть замаскирована в `finally`

**Файл:** `src/core/mixins/user.py:48-64`.

Если `send_message()` выбрасывает исключение до присваивания `message`, блок `finally` читает неинициализированную локальную переменную. Вместо исходной ошибки вызывающий код получает `UnboundLocalError`, что затрудняет диагностику сетевых/API-сбоев. Также исключение при удалении сообщения не даёт выполнить очистку `message_pool`.

**Исправление:** инициализировать `message = None` до `try`, а удаление обернуть так, чтобы очистка пула выполнялась безусловно (`try/finally`). **Проверка:** тесты с ошибкой отправки и ошибкой удаления, проверяющие сохранение исходного исключения и очистку пула.

### Medium — настройка бота прекращается при первом FloodWait

**Файл:** `src/core/mixins/user.py:125-135`.

Один общий `except FloodWait: pass` охватывает фото, имя и оба описания. Если любое раннее действие вызывает FloodWait, остальные операции молча пропускаются, а вызывающий код не узнаёт о неполной настройке.

**Исправление:** обрабатывать FloodWait на уровне отдельной операции с задержкой/ограниченным повтором или возвращать/логировать конкретный результат настройки. **Проверка:** эмулировать FloodWait на каждой операции и проверять, что политика повторов и итоговый статус соответствуют ожиданиям.

## Рекомендации и границы проверки

- `src/core/module/loader.py:21-38` исполняет код каждого модуля при импорте и `register()`. Это ожидаемая модель плагинов, но каталог модулей должен считаться доверенной границей; изолированного исполнения или проверки источника нет.
- `src/core/client.py:53-74` очищает активные модули до успешной загрузки новых. Исключение импорта/регистрации оставляет клиентов без ранее работавших обработчиков. Рассмотреть staging новой конфигурации обработчиков и атомарное переключение; покрыть сценарием частичной ошибки загрузки.
- В `config.py` параметры `SUPERADMIN_IDS` и `HANDLERS_DIR` не используются; `get_settings()` всегда выбирает HTTP proxy, хотя конфигурация также предлагает SOCKS5 accessor. Уточнить контракт конфигурации и удалить или реализовать неиспользуемые настройки.
- Критическая логика BotFather, перезапуска и маршрутизации обработчиков не имеет автоматических тестов. Добавить unit-тесты с моками, затем интеграционные проверки только на отдельном Telegram-аккаунте.

Других подтверждённых критических или высокоприоритетных дефектов в доступном коде не установлено. Это не аудит безопасности зависимостей и не проверка поведения Telegram API в сети.
