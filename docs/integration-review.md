# Интеграционное ревью Fear и Fear Module

## Связь проектов

Fear объявляет Git-зависимость на Fear Module в `pyproject.toml` и фиксирует конкретный коммит в `uv.lock` (версия `0.1.1`, коммит `321e0ae12e90a94eca4df94e68159246ac85af5f`). Fear импортирует `ClientType`/`FearModule` в менеджере модулей, создаёт экземпляры подклассов из `src/modules/*/main.py`, вызывает `register()` и назначает обработчики клиентам по типу. SDK предоставляет типы и хранение обработчиков; фактический жизненный цикл реализует Fear.

## Общая оценка

Публичный контракт используется согласованно: системный модуль передаёт host-клиент в конструктор и использует `add_commands()` и `Command.add_handler()`. `FearClientProtocol` импортируется из `fear_module.protocols`, чтобы работать с текущим зафиксированным Git-коммитом SDK; протокол также экспортируется публично в рабочей копии SDK. Строка зависимости Fear остаётся закреплённой на коммите `321e0ae...`; обновить её следует после публикации/коммита нового SDK API.

Главные оставшиеся риски интеграции: отдельные тесты SDK и Fear не образуют полного контрактного набора; загрузка плагинов исполняет доверенный код прямо в процессе. Fear теперь сохраняет старые обработчики, если новая загрузка завершается ошибкой. Подробнее: [ревью Fear](code-review.md), [ревью SDK](../../fear-module/docs/code-review.md) и [предложение формата/установки модулей](module-format-proposal.md).
