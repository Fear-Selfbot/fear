# Интеграционное ревью Fear и Fear Module

## Связь проектов

Fear объявляет Git-зависимость на Fear Module в `pyproject.toml` и фиксирует конкретный коммит в `uv.lock` (версия `0.1.1`, коммит `321e0ae12e90a94eca4df94e68159246ac85af5f`). Fear импортирует `ClientType`/`FearModule` в менеджере модулей, создаёт экземпляры подклассов из `src/modules/*/main.py`, вызывает `register()` и назначает обработчики клиентам по типу. SDK предоставляет типы и хранение обработчиков; фактический жизненный цикл реализует Fear.

## Общая оценка

Публичный контракт в основном используется согласованно: системный модуль передаёт Fear-клиент в конструктор и использует `add_commands()` и `Command.add_handler()`. Набор `test.py` в Fear Module — устаревший пример, но не используется хостом при запуске. `uv.lock` в Fear соответствует его текущим метаданным; lock-файл SDK нуждается в обновлении.

Главные риски интеграции: нет контрактных тестов SDK ↔ хост; загрузка плагинов исполняет доверенный код прямо в процессе; ошибка нового модуля при перезагрузке оставляет Fear без ранее загруженных модулей. Подробнее: [ревью Fear](code-review.md) и [ревью SDK](../../fear-module/docs/code-review.md).
